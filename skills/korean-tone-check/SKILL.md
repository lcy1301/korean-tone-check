# 한국어 말투 검사·교정

사용자의 선호는 쉬운 제품 용어, 자연스러운 문장, 과하지 않은 존댓말이다. 아래 표에서 왼쪽은 검사 후보, 오른쪽은 권장 표현이다. 순우리말 전체나 특정 모델의 모든 문체를 금지하는 규칙이 아니다.

## 적용 방법

- 기존 글을 검사할 때에는 아래 기준에 해당하는 모든 위치를 찾는다. 단어뿐 아니라 활용형과 같은 뜻의 문장 구조도 검사한다.
- 새 글을 작성할 때에는 같은 기준으로 작성하고, 출력 전에 다시 검사한다.
- 기본 결과는 `교정문`과 `변경 내역`이다. 변경 내역은 위치 또는 주변 문장, 원문, 수정문, 적용 기준을 표로 보여 준다. 같은 표현이 여러 곳에 있으면 각 위치를 기록한다.
- 사용자가 교정문만 요청하면 교정문만 제공한다. 검사만 요청하면 원문을 바꾸지 않고 수정 후보를 제공한다.
- 판단에 필요한 사실이 없으면 해당 부분을 `확인 필요`로 기록한다. 기능, 성능, 판매 조건을 추측해 채우지 않는다.

## 의미 보존과 문맥 판단

- 표현을 발견한 뒤 주체·대상·동작과 주변 문맥을 확인한다. 해당 맥락에서 권장 표현과 뜻이 같은 경우에만 수정한다. 규칙의 표현이 등장했다는 이유만으로 오류로 판단하지 않는다.
- 의미가 달라지거나 판단이 불확실하면 원문을 유지하고 `확인 필요`로 기록한다. 사실이나 제외 대상을 새로 만들어 수정하지 않는다.
- 문장을 다시 쓸 때 주체, 대상, 조건, 부정, 가능 여부, 의무·권고의 강도, 수치, 시점, 동작 순서를 보존한다. 명시적으로 삭제하도록 정한 홍보 주장·준비 중 안내는 삭제 사실을 기록한다.
- 문자열 전체 치환은 하지 않는다. 조사, 활용, 문장 구조를 함께 고친다.
- 새로 추가한 다운로드·선택·입력·추가·삭제 용어는 제품 문구와 기능 설명에 적용한다. 일반 작문까지 같은 단어를 일괄 치환하지 않는다.
- 제품 사용 안내에서는 실제 기능과 동작을 먼저 설명한다. 카운터·요리사·열쇠처럼 기술 동작을 대신하는 비유는 확인된 처리 관계로 바꾼다. 사용자가 비유를 요청했거나 비유가 이해에 필요한 경우에는 유지할 수 있다. 비유를 없애며 원문에 없는 구현 방식을 추측하지 않는다.
- 연결된 기능에는 `붙다`가 검사 후보지만, 물리적으로 물건이 붙는 설명은 유지한다. 책의 판 번호, 음식 굽기, 식물 씨앗, 실제 갈래, 직접 인용도 같은 이유로 일괄 치환하지 않는다.
- 사용자는 `고치다`보다 `수정하다`, `좁히다`보다 `제외하다`를 선호한다. 문구·문서·오류를 고치는 설명에는 `수정하다`를 사용한다. 실제 기계 수리나 질병 치료는 뜻에 맞게 유지하거나 수리·치료로 표현한다.
- 대상을 빼는 뜻의 `좁히다`는 `제외하다`로 바꾸고 제외 대상을 명확히 쓴다. 실제 폭·범위 축소는 제외와 뜻이 다르므로 유지한다. 제외할 대상을 알 수 없으면 추측하지 않고 확인 필요로 기록한다.
- 주어를 없애면 책임 주체나 대상이 모호해지는 경우 명확한 주어를 유지한다.
- 정책, 계약, 인용에 있는 `제한 없음` 같은 표현은 홍보 문구와 구분한다. 사실이나 인용을 임의로 삭제하지 않는다.
- 코드, URL, 식별자, 실제 제품명은 보존한다. 코드 속 사용자용 문자열을 고치는 요청이라면 해당 문자열에만 적용한다.
- 교정 뒤 원문과 대조해 사실, 부정, 가능 여부, 기능 조건, 수치가 달라지지 않았는지 확인한다. 의도적으로 지운 홍보 주장·준비 중 안내는 변경 내역에 남긴다.
- 규칙에 없는 취향을 사용자 선호로 추가하지 않는다. 새로 발견한 반복 말투는 추가 규칙 후보로 제안한다.

## 프런트엔드 화면 문구와 표현 형식

화면을 작성·구현하거나 UI 문구를 검사할 때 적용한다. 일반 문서와 장문 설명 요청까지 짧은 UI 형식으로 바꾸지 않는다.

- 문구를 추가하기 전에 사용자의 행동, 현재 상태 이해, 선택, 오류 해결에 필요한 정보인지 확인한다. 목적이 없는 문구는 표시하지 않는다.
- 구현 메모, 코드 주석 같은 설명, 개발자에게 하는 안내, 디자인 의도, 제작 과정, 컴포넌트 구조, 사용 기술 소개, 임시 문구는 사용자 화면에 표시하지 않는다. 사용자에게 필요한 기술 정보는 유지한다.
- 예를 들어 `이 영역은 사용자의 편의를 위해 카드 형태로 구성했습니다`, `추후 API를 연결할 예정입니다`, `SVG 아이콘을 사용했습니다`는 화면 문구에서 삭제한다. 필요한 개발 메모는 코드 주석이나 개발 문서에 둔다.
- 실제 조작 방법, 처리 결과, 가격·사용량·기능 제한, 동의·권한·보안 조건, 오류 해결 방법은 불필요한 주석으로 취급하지 않는다.
- 화면 제목·버튼·상태에서 이미 전달한 내용을 설명문으로 반복하지 않는다. 이해에 필요한 추가 정보가 있을 때만 설명을 붙인다.
- 짧게 써도 뜻이 분명하면 문장 대신 아래 형식을 선택한다. 모든 내용을 배지나 아이콘으로 바꾸지는 않는다.

| 정보의 역할 | 권장 형식 | 예시 |
| --- | --- | --- |
| 짧은 상태·등급·분류 | 알약 형태 배지 또는 짧은 텍스트 | 연결됨, 처리 중, 프로 |
| 사용자가 실행할 행동 | 버튼의 짧은 동작 문구 | 다운로드, 다시 연결, 설정 저장 |
| 서로 다른 선택지 | 선택 컨트롤과 짧은 라벨 | 내 PC / 클라우드. 클릭할 선택지를 단순 상태 배지처럼 만들지 않음 |
| 여러 조건·속성 | 라벨·값, 목록, 비교표 | 로라: 최대 3개 / 월 생성량: 1,500장 |
| 판단에 필요한 핵심 설명 | 짧은 요약문 | 생성 실패 시 사용량은 차감되지 않습니다 |
| 익숙하고 단순한 의미 | SVG 아이콘, 필요하면 짧은 라벨 병기 | 검색, 다운로드, 설정 |
| 추가 설명·세부 절차 | 도움말 또는 펼쳐 보기 | 설정 원리, 상세 사용 방법. 필수 조건은 숨기지 않음 |
| 오류·복구 안내 | 문제와 다음 행동을 짧게 설명 | PC에 연결할 수 없습니다. 커넥터를 실행한 뒤 다시 연결하세요 |

- SVG 아이콘은 장식인지 의미 전달·조작용인지 구분한다. 장식은 보조 기술에서 숨기고, 아이콘만 있는 버튼에는 동작을 설명하는 접근성 이름을 제공한다. SVG 자체가 버튼을 대신하지 않도록 의미에 맞는 버튼 요소를 사용한다.
- 뜻이 낯설거나 여러 가지로 해석될 수 있는 아이콘에는 텍스트를 함께 표시한다. 상태를 색상만으로 전달하지 않는다. 중요한 안내를 툴팁에만 두지 않는다.
- 요약하면서 조건, 단위, 기간, 수치, 부정, 오류 해결 순서를 빠뜨리지 않는다. 예를 들어 `현재 요금제에서는 로라를 1개까지 사용할 수 있습니다`는 `로라 최대 1개`로 정리하되 현재 요금제가 무엇인지 화면에서 확인할 수 있어야 한다.
- 문구만 전달받았다면 형식 변경안을 제안한다. 화면 구현 요청이라면 기존 컴포넌트와 디자인 스타일을 사용해 필요한 부분만 수정한다. 문구 개선을 이유로 요청하지 않은 기능이나 화면을 추가하지 않는다.
- 변경 내역에 삭제·요약·배지 전환·아이콘 전환과 이유를 기록한다. 실제 화면을 확인할 수 있다면 넘침·중복·라벨의 이해 가능성을 확인한다. 구현했다면 접근성 이름과 키보드 조작도 확인한다. 확인하지 못한 화면 동작을 검증했다고 주장하지 않는다.

원문: 우리가 새 판에 태그 뽑기를 얹었습니다. PC 에 안 닿으면 다시 잇는 중으로 나옵니다. 시드을 적어 주세요.

교정문: 새 버전에 태그 생성 기능을 추가했습니다. PC에 연결할 수 없으면 ‘다시 연결하는 중’으로 표시됩니다. 시드를 입력하세요.
